# Operator-only testing and private support

Use this workflow for real files. The assistant never runs it for you, opens the operator UI, lists folders, reads filenames, or looks for exports on disk. You decide what sanitized information to share.

## Isolation before the first file

VideoMate is a development preview. Sensitive mode is not encryption, an OS sandbox, or proof of complete security. For a strict boundary from assistant tools, run it on a separate approved offline workstation or isolated environment that this assistant cannot access. Use organization-approved encrypted local storage and access controls. Keep media, settings, workspaces, mappings and recovered files outside this checkout, OneDrive and other synced folders. VideoMate does not configure host protections or erase historical data.

Transfer an approved complete release or the current source with its prepared dependencies to that environment. Start with --offline. Do not share the screen, input dialogs, terminal history or private workspace with the assistant. The operator alone selects the input files.

## First operator run

1. For current development source, run `start.bat --offline` on Windows or `sh start.sh --offline` on macOS/Linux. Source launches use current edits without rebuilding binaries; verify the version of any extracted desktop package before use.
2. Leave **Sensitive: Yes** selected. In Settings choose approved private workspace/output/diagnostic locations. Leave **Additional diagnostics** off unless you want the enhanced safe disk log. The checkbox beside Sensitive enables it in either mode; Settings controls its folder. This never enables raw logging.
3. Select a small batch yourself and run **Inspect** first. Full inspection uses software decoding so GPU error concealment cannot classify damaged inputs as healthy. CPU threads default to available logical CPUs minus two, shared across the batch; Settings can cap the scan runners. No assistant tool should access the program or files during this step.
4. In Activity, choose **Export diagnostic log** before closing the app. New Sensitive jobs retain only the most recent eight sanitized session reports in memory, with no persistent source-path journal or filename mappings. Only deliberate export writes a sensitive diagnostic report. It creates one `diagnostics-<random>.log` from validated facts in the configured diagnostics location, with repeated patterns grouped. For machine-readable analysis, CLI `export-diagnostics --job <id> --workspace <local-workspace> --technical-json` additionally writes JSON batches for a saved job. Memory-only sessions must be exported from their owning app before it closes; another CLI process cannot retrieve them. CLI users should request `--export-on-completion` during the run.
5. Review the exported text log locally. Never share the workspace, SQLite databases, mapping files, event logs, screenshots, crash dumps, console history or raw FFmpeg output. A schema check is not proof of anonymity; approved technical details can still be distinctive.
6. If you chose the optional technical JSON export, you can create a smaller identifier-free support summary. Run the following yourself with that JSON file, replacing the example path locally:

```text
start.bat --offline --cli support-summary "<your sanitized diagnostic export>"
```

On macOS/Linux, use `sh start.sh --offline --cli support-summary ...`. This command accepts JSON, not the text log. It reads only the export you select, validates it before printing, and emits versions, OS/architecture, aggregate finding/outcome counts, migration failure reasons, worker stages, resource-limit categories and fixed decoder/encoder names. It removes file/job references, times, stream details and all locators. Review its output, then paste only that summary into the chat. It does not upload anything. Activity output can include private byte sizes; share the reviewed export or support summary instead of raw Activity text.

Share only the consolidated diagnostic text log or optional diagnostic JSON you have deliberately reviewed. The underlying approved facts permit scoped HMAC identifiers, playback-relative timestamps and approved codec properties, plus worker stage, elapsed milliseconds, thread allocation, decoder/encoder, exit code, limit reason and fixed error categories/counts. Per-attempt verification reasons and rate policy explain repair outcomes. Diagnostics remain available in the session even when Additional diagnostics is off; that checkbox controls the separate disk log. Filenames, paths, metadata text, raw backend messages, source hashes and keys are excluded. Each export uses a fresh secret/scope. Sensitive jobs never write an export mapping; non-sensitive mappings require opt-in. Never share old mappings, checkpoints, keys or passphrases.

For restartable Sensitive work, enable **Private resume** before the job. After interruption, reselect the same files and use the local job ID/passphrase with Activity's private scan/repair resume action. Matching reads all selected content locally, without saving paths. The checkpoint contains readable technical results and authenticated keyed hashes; it is private and not encrypted. Completion removes it. Changing source content, application/backend version or repair policy requires a new job. [Exact steps and limitations](recovery-options.md).

If failure occurs before a job exists, report only the fixed VideoMate error code/message and the action you clicked. Do not paste an arbitrary operating-system or driver error. The assistant can add a specific closed diagnostic category if needed, using generated test cases.

## Repair and acceleration

For mixed folders, select Migrate a folder on Start and choose exactly one source folder. Choose the unresolved-file policy before starting: exclusion with reported omissions is the default; unchanged package copies or a separate review folder are optional. Choose an empty destination and click Start new migration; new output files land directly in that destination. If Sensitive local-name permission is missing, approve or decline the prompt before processing. Preview is optional. Review the adjacent `<destination-name>.status.json` and any requested review copies locally. Never share package contents or their names with the assistant. Migration can reconnect in-session automatically. After Stop, use **Continue stopped migration** with the same selections and policy while the app stays open. Enable Private resume before starting for restart recovery; later use **Activity → Resume from private checkpoint…** with the original Job ID/passphrase and the same source, destination and options. Only generated-fixture tests are permitted for assistants; operator checkpoints are private. [Complete workflow](migration-and-profiles.md).

Preview the repair plan before running it. Originals are preserved and each output is independently verified. Missing bytes cannot be recreated.

The current source's **Use available hardware encoding** option applies only to Compatible SDR H.264/AAC repair. It tries supported NVIDIA NVENC, Intel QSV, AMD AMF or Apple VideoToolbox encoders using three generated black frames, then software-decodes that generated output. Merely appearing in `ffmpeg -encoders` is insufficient. Readiness is cached for that job. Actual repair failure or verification failure first retries with software decoding while retaining the hardware encoder, then falls back to libx264 within a maximum of four codec attempts including remux. Source/target size policies permit one additional bitrate-adjustment attempt; cancellation/resource limits stop work. No driver names, identifiers or raw probe output enter diagnostics.

H.264 now defaults to an estimated source bitrate, with configurable quality, bitrate and approximate size policies. Quality uses CRF 18 by default on software; hardware uses the Auto estimate. Use Preserve decoded samples for FFV1/PCM. Candidate verification always uses software decoding. Preservation and remux do not become lossy H.264 because hardware is enabled. Eligible re-encoding can use hardware decoding: D3D11VA/DXVA2/CUDA/QSV on Windows, VideoToolbox on Apple Silicon, and CUDA/VAAPI/QSV on Linux. Each host must pass a generated H.264 hardware-frame download check; support for other codecs/profiles is checked by the actual attempt. Combined decoder/encoder paths are qualified once with generated frames; incompatible pairs keep GPU encoding with software decoding. Authoritative inspection and candidate verification always use software decoding. Limits and cancellation stop work. HDR/interlaced conversion remains limited by the existing policy. New acceleration paths still need native Mac/Linux validation at the deferred checkpoint.

Parallel inspection assigns each active file a share of one codec thread budget. Automatic Inspect runners are bounded by the available budget and batch size; integrity scans use software decoding. Migration defaults to up to four concurrent files, one verified copy and two GPU jobs; its GPU admission is configurable. It distributes workers across generated-frame-qualified codec APIs, not individual cards behind the same API. Set **Parallel files** lower for slow disks or limited memory. Standalone Repair stays serial. This requests codec parallelism, not an OS CPU reservation: worker I/O, drivers and FFmpeg helper threads add overhead. More runners may not be faster on a saturated drive.

For migration that keeps healthy files unchanged and targets similar repair sizes, select **Migrate — repair to MP4** or **Use source-size MP4 defaults**. This turns off temporary caps and selects source-size MP4 recovery with hardware preferred. Automatic MP4 recovery tries verified stream copy first; encoding fallback is lossy. Choose preservation when decoded-sample retention is required. Final size is checked separately, with one adjustment retry above the tolerance (default +25%); smaller verified files are kept without padding. Low-disk protection remains active. Existing saved caps remain until changed or the preset is applied. Loudness normalization, AAC bitrate, software speed and fast-start are optional advanced controls; normalization is off by default and does not affect healthy copies unless all-file conversion is chosen. `candidate_limit` means an optional temporary cap was reached; `size_target_exceeded` means the finished encode did not meet the size policy. Neither establishes irrecoverability. Share the reviewed support summary, which includes fixed recovery-note counts without sizes or names.

## Fast iteration

Share the reviewed summary and a short description of the unexpected behavior, without source names or content. The assistant implements features first. Broad suites, the full CI matrix and platform rebuilds are deferred to an explicit checkpoint; pushes do not trigger the full matrix. Only necessary focused privacy/recovery checks accompany changed behavior. Runtime validation, output verification and privacy controls remain enabled. Tagged releases retain their native validation gate. Close and reopen the source GUI to pick up changes; do not switch code underneath a running job.
