# Migration interruption recovery

Live reconnect rechecks completed source/output hashes after workers stop; missing or changed publications stop for review. Backend startup failures can receive bounded temporary-failure retries. A stopped memory-only migration can continue in the same app session. Completed jobs with exclusions/failures use [session-only unresolved retries](completed-jobs-and-retries.md). Neither can reconstruct old work from diagnostic exports.

Version 0.8.4. All development checks use generated files; assistants must never inspect operator media, filenames, checkpoints or private state.

## Starting and resuming

**Migration interruption recovery** is on by default. Start shows both interruption options before a new migration: **continue in this app after Stop** and optional **also resume after closing**. The latter creates a private checkpoint and requires a passphrase. With interruption recovery on, VideoMate waits for the selected source/output storage to return, verifies its identity and the package ownership marker, rediscovers only the selected source tree, and retries transient file I/O failures or worker timeouts up to **three retries after the initial attempt**. Each retry round drains its workers before replacement work starts. Stop interrupts storage waiting and backoff; a disconnected drive can remain in the waiting state until it returns or the operator stops. Actual damaged/unsupported media does not enter an unlimited repair loop.

If a memory-only migration stops while the app remains open, keep VideoMate open. On **Start**, select **Migrate a folder**, reselect the same source folder and destination, keep the original recovery options, and click **Continue stopped migration**. The same action appears on **Activity** beside the Job ID. To work on another collection instead, choose **Start a different migration…** and use a new empty destination; keep the original Job ID if you plan to return to the stopped package. VideoMate verifies the selected tree and published outputs before processing unpublished work. This session snapshot disappears on app close.

For recovery after closing the app or restarting the computer, select **Also resume after closing** on Start before the first migration (the same switch is in Settings). Create and confirm a passphrase of at least 12 characters when prompted. It is supported for migration in either Sensitive mode. Keep the Job ID from the top of Activity and the passphrase privately; **Copy ID** writes the ID to the system clipboard, which may be synced by OS settings. Later, choose **Migrate a folder** on Start, reselect the same source and destination, restore the same processing options, then open **Activity**, enter the original Job ID, and click **Resume from private checkpoint…**. Enter the original passphrase when prompted. This reuses the original package. **Resume after closing…** on Start takes you to those Activity controls. A completed package with no checkpoint, or a job that started without Private resume, cannot be reconstructed from diagnostic exports. Starting a new migration requires an empty destination; it cannot adopt an existing package.

When a stopped session-only job or unresolved retry is available, closing VideoMate warns that its in-memory state will be lost. The main Start button becomes **Continue stopped migration** while that continuation is available. A failed resume attempt leaves the Job ID visible so it can be corrected and retried. The Activity screen shows Job ID and continuation controls above the bounded log.

If a completed migration has unresolved items while VideoMate is still open, reselect the same source and destination on Start. On Activity, click **Preview unresolved retry**, review the result, then **Start unresolved retry**. This is a separate path from continuing a stopped job. Its session snapshot also disappears when the app closes.

CLI equivalents (operator-only; replace placeholders locally):

```text
start.bat --offline --cli migrate --workspace <workspace> --input <source-folder> --local-output-names --private-resume
start.bat --offline --cli migrate --workspace <workspace> --input <source-folder> --local-output-names --checkpoint <job-id>
```

Use `sh start.sh --offline --cli ...` on macOS/Linux. Preserve any original output/profile/options on the second command. The passphrase is prompted locally, never passed as a CLI argument or saved in settings. `--no-interruption-recovery` disables automatic reconnect/retries; an enabled restart checkpoint remains available. A preview never creates a checkpoint.

If returned storage has a different identity, its ownership marker is missing/changed, the source manifest/metadata changed, a completed source's bytes changed, or an output differs from its recorded verified bytes, resume stops and asks for local review. It does not overwrite, force-adopt or search other drives. A remount that changes filesystem identity can require review even when it is physically the same device. Changed policies/source sets require a new job. This is intentionally stricter than matching a drive letter or filename.

## Privacy and durable publication

Without Private resume, the journal is SQLite in memory and the matching key is random and session-only. With Private resume, `state/migration-<random-id>.sqlite3` contains keyed relative-name/stat/manifest/content identifiers and closed-schema technical results. It contains no source/output paths, real filenames, raw content hashes, passphrase, raw logs or command lines. A random salt and PBKDF2-HMAC-SHA256 (600,000 iterations) derive the key; metadata and each result are authenticated. The indexed journal has no 1,000-input ceiling and does not rewrite all completed records for each completion. The source inventory and in-memory session report still scale with input count and available RAM.

Checkpoints **are private, linkable and not encrypted**. Technical facts remain readable. Weak passphrases can be attacked offline. They are never diagnostic exports and must never be shared with an assistant. Settings retain only the feature switches. No organization deployment certification or OS sandbox is implied.

A verified copy or repair records a durable publication intent before the no-overwrite final move. The record includes keyed source/output checksums and a closed output kind; destinations are reconstructed from the operator's selected tree. After a crash between publication and completion reporting, the next run checks both source and output bytes and reuses the output. Missing outputs are processed again; changed/untracked outputs are left for review. A repair candidate still requires independent full software verification before an intent can be recorded. Plain-text exports contain no checkpoint identifiers or locators.

On full completion, the optional checkpoint is closed and removed. Interrupted, failed and needs-review checkpoints remain for explicit resume. Private-checkpoint jobs use that checkpoint rather than an independent session retry snapshot, so the persisted state stays authoritative. Deletion is ordinary deletion, not secure erasure. Package status and a small neutral ownership sidecar remain beside the package. An old migration created without this feature cannot be retrospectively resumed from its diagnostic log.

## Scheduling and leftover handling

One processing coordinator is admitted per application process and per workspace across processes. Its CPU allocation is shared by bounded worker lanes; this is an FFmpeg thread request, not a hard OS thread/CPU reservation. Separate processes using different workspaces are not globally coordinated. Mixed migrations reserve a copy lane; verified copies and restart hash checks share one I/O gate. Worker/backend objects belong to individual lanes; job/UI result updates stay on the coordinator. The private intent journal serializes transactions through a lock. Retries use fresh round cancellation, never clearing the operator's Stop flag.

After workers have stopped and returned storage is verified, a sweep examines only the current run's exclusively created staging directory, checking its filesystem identity. Recognized neutral candidates can be removed; unrecognized/unavailable entries are retained, including during final cleanup. If worker shutdown cannot be confirmed, no retry or candidate deletion occurs, and the current app process refuses new jobs. Confirm worker exit locally before restarting the app. Previous runs' unclaimed staging folders are not automatically erased, adopted or executed. An OS filesystem call stuck inside a driver may delay Stop; VideoMate cannot safely bypass it by launching duplicate workers. A restarted job checks all selected inputs against the checkpoint; missing/failed work is retried and unresolved originals remain untouched.

NVIDIA NVENC routes probe device indices 0–15 with generated frames and software verification, including when the default adapter fails, and bind CUDA decoding/NVENC encoding to a qualified index. Admission gates remain separate per qualified route. File-lane defaults grow to the qualified route count within the CPU budget; an explicit Parallel files cap still wins. If a GPU route fails on a file, recovery tries the remaining qualified GPU encoders before software encoding. A route that publishes a fully verified output becomes that lane's first choice for later files; failures on one file do not globally disqualify a GPU. AMD AMF, Intel QSV and Apple VideoToolbox retain their qualified default adapter; multiple identical AMD/Intel adapters are not explicitly enumerated. GPU identities and driver text are never exported. See FFmpeg's [device selection](https://ffmpeg.org/ffmpeg.html#Advanced-Video-options) and [NVENC GPU option](https://ffmpeg.org/doxygen/trunk/nvenc__h264_8c_source.html).

Full inspection and final candidate verification always use software decoding because hardware concealment can hide corruption. FFV1 preservation remains software-based. Pending files use a keyed name/stat manifest rather than a full prehash; content edits deliberately preserving all filesystem metadata may not be detected before those pending files are processed anew. Restart verification rereads completed sources/outputs and can be I/O-bound; verified copy checksums are reused during the initial run to avoid redundant hashing. Persistent per-file intents require durable journal writes, so restart safety adds storage latency. Device qualification may also add startup time. No universal speedup or physical multi-GPU/native macOS qualification is claimed from mocked tests.
